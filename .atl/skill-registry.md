## Project Skills (.agents/skills/)

### `vercel-react-best-practices`
**Trigger**: Writing, reviewing, or refactoring React components; data fetching; bundle optimization; performance improvements.

**Compact Rules**:
- Prefer Server Components by default; use `'use client'` only when needed (interactivity, browser APIs)
- Avoid `useEffect` for data fetching — use RSC, SWR, or React Query
- Memoize with `useMemo`/`useCallback` only when profiling confirms benefit
- Use `React.lazy` + `Suspense` for code splitting at route/feature boundaries
- Keep components small and single-responsibility
- Co-locate state as close to where it's used as possible
- Use `key` prop correctly — never use array index as key for dynamic lists
- Prefer composition over prop drilling; use Context sparingly (for truly global state)

### `vercel-composition-patterns`
**Trigger**: Compound components, render props, context providers, component architecture, boolean prop proliferation, flexible/reusable component APIs. React 19 API changes.

**Compact Rules**:
- Prefer compound components over boolean prop explosion (`<Tabs>`, `<Tabs.List>`, `<Tabs.Panel>`)
- Use `children` and `render props` for flexible composition
- Context providers should be narrow — wrap only what needs the context
- React 19: `use(Promise)` replaces `useEffect` for async reads; `useOptimistic` for optimistic UI
- React 19: `ref` is now a regular prop — no more `forwardRef` wrapper needed
- React 19: `<form action={fn}>` for progressive enhancement
- Avoid HOCs — prefer hooks and composition
- Document component contracts clearly (what props, what slots, what context)

### `tailwind-css-patterns`
**Trigger**: Styling React/Vue/Svelte components, building responsive layouts, implementing design systems, optimizing CSS workflow with Tailwind.

**Compact Rules**:
- Use utility classes directly — avoid `@apply` except for base element resets
- Tailwind v4: config is CSS-first (`@theme` in CSS), no `tailwind.config.js` needed
- Use `gap-*` for flex/grid spacing, not margins between siblings
- Responsive: mobile-first (`sm:`, `md:`, `lg:`) — style base for mobile, override up
- Dark mode: use `dark:` variant; configure with `@variant dark` in CSS
- Use `group` and `peer` for sibling/parent-child interaction states
- Prefer `size-*` shorthand over `w-* h-*` when both are equal
- Use `text-balance` / `text-pretty` for headings and body text respectively
- Custom values: use `[value]` arbitrary syntax sparingly; prefer design tokens in `@theme`

### `typescript-advanced-types`
**Trigger**: Complex type logic, reusable type utilities, compile-time type safety, generics, conditional types, mapped types, template literals.

**Compact Rules**:
- Prefer `interface` for object shapes that may be extended; `type` for unions, intersections, computed types
- Use `satisfies` operator to validate against a type without widening
- Discriminated unions > optional props for state modeling
- `infer` in conditional types for extracting inner types
- `as const` for literal inference; `readonly` arrays to prevent mutation
- `NoInfer<T>` (TS 5.4+) to prevent unwanted inference in generic functions
- Use `Awaited<T>`, `ReturnType<T>`, `Parameters<T>` before writing custom utilities
- Avoid `any` — use `unknown` and narrow; use `never` for exhaustive checks

### `vite`
**Trigger**: Working with vite.config.ts, Vite plugins, Vite 8 / Rolldown migration, SSR, library mode.

**Compact Rules**:
- Vite 8 uses Rolldown by default — most Rollup plugins still work but verify compatibility
- Use `import.meta.env.VITE_*` for env vars (must be prefixed `VITE_`)
- `defineConfig` with `plugins: []` — keep plugins minimal and ordered (transforms before framework plugins)
- For library mode: set `build.lib` + `build.rollupOptions.external`
- Use `resolve.alias` for path aliases (mirror in tsconfig `paths`)
- `optimizeDeps.include` for CJS deps that need pre-bundling
- HMR: `import.meta.hot.accept()` for manual HMR boundaries
- Use `vite preview` to test production build locally before deploy

### `frontend-design`
**Trigger**: Building web components, pages, dashboards, HTML/CSS layouts, or when styling/beautifying any web UI with high design quality.

**Compact Rules**:
- Design with intent — every visual decision should serve a purpose
- Use 8px base grid for spacing consistency
- Typography scale: use a modular scale (1.25× or 1.333×); limit to 2 font families max
- Color: define semantic tokens (background, surface, border, text-primary, text-secondary, accent)
- Avoid generic AI aesthetics — no purple gradients, no glassmorphism unless intentional
- Prioritize content hierarchy: size, weight, color, spacing in that order
- Motion: prefer `transition` over keyframes for micro-interactions; respect `prefers-reduced-motion`
- Production-grade means accessible: sufficient contrast, focus states, semantic HTML

### `accessibility`
**Trigger**: Accessibility audits, WCAG 2.2 compliance, screen reader support, keyboard navigation, a11y improvements.

**Compact Rules**:
- WCAG 2.2 AA minimum: 4.5:1 text contrast, 3:1 large text/UI components
- All interactive elements must be keyboard-accessible (focusable, operable with Enter/Space)
- Use semantic HTML first — `<button>`, `<nav>`, `<main>`, `<article>` before adding ARIA
- ARIA: only add roles/attributes when semantic HTML is insufficient; never override native semantics
- Images: `alt` text for informative images; `alt=""` for decorative
- Forms: every input needs a visible `<label>` (not just placeholder)
- Focus management: trap focus in modals; restore focus on close
- Skip links: provide "Skip to main content" as first focusable element

### `seo`
**Trigger**: SEO optimization, meta tags, structured data, sitemap, search engine visibility.

**Compact Rules**:
- Each page needs unique `<title>` (50–60 chars) and `<meta name="description">` (150–160 chars)
- Use semantic HTML headings hierarchy: one `<h1>` per page, logical `h2`→`h3` nesting
- Add Open Graph tags (`og:title`, `og:description`, `og:image`) for social sharing
- Structured data: use JSON-LD `<script type="application/ld+json">` for rich results
- Images: descriptive `alt` text, use `<picture>` with WebP + fallback, add `width`/`height`
- Core Web Vitals: LCP < 2.5s, CLS < 0.1, INP < 200ms
- Canonical URLs: `<link rel="canonical">` to avoid duplicate content
- sitemap.xml + robots.txt at domain root

### `nodejs-best-practices`
**Trigger**: Node.js architecture decisions, framework selection, async patterns, security, backend thinking.

**Compact Rules**:
- Understand the problem before picking a framework (Express for simplicity, Fastify for performance)
- Always handle promise rejections — unhandled rejections crash Node 15+
- Use `async/await` over callbacks; avoid Promise chains where `await` is clearer
- Environment config via `process.env`; validate with zod or envalid at startup
- Separate concerns: routes, controllers, services, repositories
- Never trust user input — validate and sanitize at the boundary
- Use structured logging (pino, winston) not `console.log` in production
- Graceful shutdown: handle `SIGTERM`/`SIGINT`, drain connections before exit

### `nodejs-backend-patterns`
**Trigger**: Creating Node.js servers, REST APIs, GraphQL backends, microservices, Express/Fastify middleware.

**Compact Rules**:
- Middleware order matters: security → body parsing → auth → routes → error handling
- Centralize error handling in a single error middleware (Express) or `setErrorHandler` (Fastify)
- Use `helmet` for security headers, `cors` with explicit origins, `express-rate-limit` for rate limiting
- Auth: verify JWT in middleware, never in route handlers; use `httpOnly` cookies for tokens
- Database: use connection pooling; never build SQL strings with user input (use parameterized queries)
- Validation: validate request body/params/query at the route boundary (zod, joi, or Fastify's schema)
- Async route handlers must catch errors — use `express-async-errors` or wrap manually
- Health check endpoint (`GET /health`) for load balancers and k8s probes
